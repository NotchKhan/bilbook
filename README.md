# BilBook · первая версия

Закрытое школьное сообщество БИЛ / КТЛ: фотоистории, новости, школьные проблемы и конфиденциальные обращения. Интерфейс на русском, сначала одна школа; все данные изолируются по `school_id`.

**Текущий статус:** GitHub, Supabase и Vercel подключены. Рабочий сайт: https://bil-book.vercel.app/. Создана школа и первоначальный администратор. На `/` требуется вход по приглашению; `/demo` содержит отдельные вымышленные примеры и ничего не сохраняет. Состояние проверок — в docs/RESULTS.md.

[Результаты проверок и скриншоты](docs/RESULTS.md) · [Архитектура и доступы](docs/ARCHITECTURE.md) · [Проверки после подключения](docs/VERIFICATION.md)

Тёмный интерфейс по пользовательским референсам социальных сетей: [docs/DESIGN.md](docs/DESIGN.md). Единые стили — `src/app/globals.css`.

## Запуск без внешних сервисов

Нужен Node.js 22+; проверено на Node.js 24.16.0 / npm. В папке проекта:

```powershell
npm ci
npm run dev
```

Открыть `http://127.0.0.1:3000`. Демонстрация: `http://127.0.0.1:3000/demo`.

```powershell
npm run typecheck
npm test
npm run build
npm audit --omit=dev
```

Для production-сборки после `npm run build`: `npm start`. Скрипты разработки и локального запуска слушают только loopback. Для самостоятельного хостинга задайте нужный hostname в своей команде запуска.

## Что реализовано в коде

- Приглашения с привязкой к школе, сроком, лимитом использований, отзывом и хешированием кода. Триггер Auth не позволяет зарегистрироваться без действительного приглашения, включая прямой вызов Auth API.
- Email/password, подтверждение email, PKCE callback, восстановление и смена пароля, выход. Серверные cookie HttpOnly, SameSite=Lax, Secure в production.
- Имя, аватар, необязательные класс и дормиторий. Нет полей ИИН, адреса, даты рождения и телефона.
- Роли ученик / учитель / модератор / администратор. Редактор и ответственный взрослый назначаются отдельно. Метаданные Auth не являются источником прав.
- Фотоистории с предпросмотром и подписью, просмотром и переключением, удалением и жалобой. Пять публикаций за скользящие 24 часа; удаление не возвращает лимит.
- Фото до 8 МБ исходного размера: браузер сжимает до 1600 px / 3 МБ, сервер проверяет настоящий формат и снова перекодирует в WebP, удаляя EXIF. JPEG / PNG / WebP, до 40 Мп. Видео не предлагается.
- Четыре категории новостей; публикации редакторов, постоянное хранение, уникальные лайки, удаление уполномоченным пользователем.
- Публичные проблемы проходят ручную модерацию; имя автора хранится отдельно от школьной ленты. Уникальная поддержка, ответ, четыре статуса, история изменений.
- Личные обращения доступны автору и назначенным взрослым. Модератор студсовета и обычный администратор автоматически доступа не получают. Фото защищены теми же проверками.
- Панель приглашений, участников и блокировок, публикаций, жалоб, обращений и журнала действий. Журнал не копирует тексты, ответы и коды приглашений.
- RLS для всех пользовательских таблиц; изменения через транзакционный RPC с проверками. Storage приватный: клиент не может читать его напрямую или выпускать ссылки произвольного срока.
- Защищённая повторяемая очистка файлов, очередь повторных попыток, обработка удаления аккаунта, серверная валидация, ограничение частоты действий, проверка Origin, CSP.
- PWA manifest, PNG-иконки 192/512, установка по событию браузера и инструкция для iPhone. Service worker не кэширует запросы и школьные материалы.
- Пагинация лент по `(created_at,id)`, по 20 записей; страницы истории обращения ограничены 50 последними событиями.

## Подключение Supabase — финальный этап

1. Создайте **новый** Supabase-проект. Не запускайте первую миграцию поверх существующего приложения: она задаёт собственные таблицы и права функций в `public`.
2. Выполните `supabase/migrations/202610210001_core.sql` в SQL Editor. Альтернатива: Supabase CLI `supabase link --project-ref ...`, затем `supabase db push`. Миграция создаёт таблицы, триггеры Auth, RLS, RPC и приватный bucket `school-media`.
3. В Auth включите Email + Password, **Confirm email**, запретите anonymous sign-ins, оставьте signup включённым — приглашения проверяет триггер. Настройте Site URL и оба Redirect URL: `https://ваш-домен/auth/callback` и `https://ваш-домен/auth/callback?reset=1`. Не используйте широкий wildcard для чужих доменов.
4. Подключите собственный SMTP для школьных адресов и настройте лимиты Supabase Auth. Встроенная почта предназначена для ограниченного тестирования, а не рассылки всей школе. Прямые запросы к Supabase Auth также должны ограничиваться его собственными лимитами. Сначала проверьте доставку, подтверждение и восстановление на тестовых аккаунтах.
5. Скопируйте `.env.example` в `.env.local`. Укажите публичный project URL / publishable key, серверный `SUPABASE_SERVICE_ROLE_KEY`, точный `APP_URL` без завершающего `/`, два разных случайных секрета не короче 32 символов для `CRON_SECRET` и `RATE_LIMIT_SECRET`. Например, сгенерировать значение: `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`.
6. Никакой service-role ключ, пароль БД или SMTP-пароль не должен иметь префикс `NEXT_PUBLIC_`. Не вставляйте секреты в Git, скриншоты или сообщения. Настоящий `.env.local` игнорируется Git.
7. Перезапустите приложение. CSP автоматически использует origin из публичного URL Supabase, включая локальный CLI.

Для локального Supabase подготовлен `supabase/config.toml`. Его запуск требует отдельно установленного CLI и Docker: `supabase start`, затем локальные миграции. Эти сервисы на текущей машине не запускались. PGlite-тесты не требуют Docker.

### Первый администратор

Откройте `supabase/bootstrap.sql`. Первая команда создаёт школу и одноразовое приглашение на сутки. Измените название школы, выполните команду **вручную как владелец проекта**, сохраните выданный код. Зарегистрируйтесь обычным способом и подтвердите email.

В Auth Users найдите точный UUID подтверждённого пользователя. Раскомментируйте второй блок bootstrap-файла, подставьте UUID и выполните отдельно в SQL Editor. Он проверяет подтверждение email и отсутствие администратора этой школы. Публичного маршрута начального повышения прав нет.

После этого приглашения и роли управляются через панель. Учителю для публикаций нужен флаг «Редактор новостей». Для конфиденциальных обращений назначьте **проверенного взрослого сотрудника** с ролью учитель или администратор и флагом «Ответственный взрослый». Код не определяет возраст по имени; личность проверяет школа. Собственные права в панели менять нельзя — для этого нужен другой администратор или владелец БД.

## Очистка историй

`expires_at = created_at + 24 hours`. RLS не выдаёт истёкшие истории и их фото сразу, независимо от cron. Фото доступно через серверный `/api/media/:id` после проверки пользовательской RLS. Ссылка живёт до 60 секунд, для истории — меньше оставшегося времени; дополнительно проверяется фактический `exp` выданного Storage-токена.

В `vercel.json` задан ежедневный `GET /api/cron/cleanup` в 02:00 UTC (07:00 Asia/Qyzylorda). Настройте Vercel environment variable `CRON_SECRET`; Vercel передаёт `Authorization: Bearer ...`. Без корректного секрета маршрут отвечает 401. Не передавайте секрет в URL.

Порядок: истёкшие stories удаляются из БД, триггер сохраняет путь в очереди `media.state=deleting`; затем удаляется Storage-объект и только после успеха — строка media. Сбой оставляет строку для повторной попытки с backoff до суток. Повторный запуск и уже отсутствующий файл безопасны. Истории и файлы обрабатываются отдельно от аккаунтов, новостей и обращений. Незавершённые загрузки старше часа тоже попадают в эту очередь; успешные постоянные публикации не затрагиваются.

Один HTTP-запуск обрабатывает партии по 100 объектов, продолжая примерно до 40 секунд. Ответ содержит `removed`, `failed`, `more`; `failed > 0` возвращает HTTP 207. Если `more=true` или очередь стабильно растёт, повторите защищённый вызов или увеличьте частоту расписания. HTTP 207 не все системы считают ошибкой: проверяйте поле `failed` в мониторинге.

**Vercel Hobby:** cron максимум раз в сутки, запуск может смещаться в пределах часа. Физические файлы после истечения могут храниться ещё около суток и дольше при сбоях/очереди, но школьная выдача уже закрыта. Для почасового cron Vercel нужен Pro. Опциональный иной планировщик должен вызывать тот же защищённый маршрут; автоматического подключения стороннего сервиса здесь нет.

Диагностика владельцем БД, без чтения конфиденциальных текстов:

```sql
select state, count(*), min(created_at) as oldest from public.media group by state;
select id, attempts, next_retry_at from public.media where state='deleting' order by next_retry_at limit 100;
```

## GitHub и Vercel — после подключения базы

Проект готов для корня отдельного приватного репозитория. Ничего не отправлено в GitHub и не опубликовано.

1. Создайте приватный репозиторий, перенесите **содержимое этой папки**, включая `.github`, `.env.example`, SQL и lockfile. Не переносите `node_modules`, `.next`, `.env.local`.
2. Выполните `git init`, `git add .`, проверьте `git diff --cached`, затем коммит и push в свой репозиторий. Workflow `.github/workflows/check.yml` проверяет типы, тесты, сборку и зависимости без секретов и без реальной БД.
3. После разрешения на публикацию импортируйте репозиторий в Vercel как Next.js. Node 24, install `npm ci`, build `npm run build`. Добавьте переменные `.env.example` в окружение Vercel. Supabase-ключи production не следует отдавать произвольным PR preview-сборкам; используйте отдельный тестовый Supabase для preview.
4. Укажите окончательный HTTPS-домен в `APP_URL` и Redirect URLs Supabase, затем пересоберите приложение. Для preview нужны отдельные точные адреса и переменные; Origin сверяется с `APP_URL`.
5. Проверьте функциональные сценарии из `docs/VERIFICATION.md`, затем ежедневную задачу и её ответ. До этих проверок интеграция и деплой не считаются подтверждёнными.

## Установка на телефон

Android/Chrome: меню ⋮ → «Добавить на главный экран» / «Установить приложение». Собственная кнопка появляется только при реальном событии `beforeinstallprompt`.

iPhone/Safari: «Поделиться» → «На экран “Домой”» → «Добавить». Нужен HTTPS, кроме локальной разработки. Приложение работает через сеть; офлайн-чтение школьных материалов не предусмотрено. При выходе сессия завершается, приложение очищает своё состояние и не оставляет приватные API-ответы в PWA-кэше.

## Расходы и ограничения

Старт возможен без платных сервисов в пределах их квот. На дату проверки [Supabase Free](https://supabase.com/pricing): 500 МБ БД, 1 ГБ файлов, 5 ГБ egress и отдельные 5 ГБ cached egress; проекты могут приостанавливаться после недели бездействия. Pro начинается от $25/месяц. Выбирайте тариф после оценки реальных объёмов и нужных резервных копий.

[Vercel Hobby cron](https://vercel.com/docs/cron-jobs/usage-and-pricing) ограничен одним запуском в сутки. Более частый cron требует Pro; тарифы, назначение Hobby и лимиты проекта нужно сверить перед школьным запуском. Возможны расходы на домен, SMTP, хранилище, трафик и платный хостинг. Файлы сжимаются до отправки с учётом [лимитов Functions](https://vercel.com/docs/functions/limitations).

Удаление фото уменьшает занятое место, но **не возвращает уже использованный трафик**. Например, 500 учеников × 2 фото × 250 КБ — около 250 МБ новых файлов в день; 20 просмотров каждого фото — уже примерно 5 ГБ передачи в день до влияния кэшей. Приватные короткие ссылки не следует считать гарантией выгодного CDN-кэширования.

В v1 нет видео, комментариев, личных сообщений, общей ленты филиалов, push-уведомлений, автоматической классификации жалоб и казахского перевода. Перевод добавляется в отдельный словарь на следующем этапе; русский UI и имена категорий централизованы частично в `src/lib/types.ts`. Нет мониторинга с отправкой уведомлений: подготовлены диагностические ответы и запросы. Дополнительные ограничения безопасности и удаления описаны в `docs/ARCHITECTURE.md`.
